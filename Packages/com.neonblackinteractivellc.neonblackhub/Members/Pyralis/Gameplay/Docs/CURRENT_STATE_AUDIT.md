# NeonBlack Gameplay Current State Audit

This is the short current-truth audit for Game Studio Core. It should stay concise enough that a new agent can read it before touching gameplay or authoring code.

## Current Architecture State

NeonBlack Gameplay is built around one runtime path and one reflective authoring spine:

```text
Gameplay code and contracts
  -> reflection + dependency tree + validators
    -> resolved authoring graph
      -> Overview / Intent / Guide / Map / Hygiene / Facts
```

Runtime starts from `GameplaySessionBootstrap` and composes through `GameplayLifetimeScope`. Session data is authored through `SessionDefinition`, `GameModeDefinition`, `ParticipantDefinition`, and `PawnDefinition`. The lifetime scope owns the visible service graph entrypoint; feature activation evidence lives in `RuntimeFeatureServicePolicy`; and service registration mechanics live in focused composition installers so the entrypoint stays readable.

Loaded-scene feature evidence uses one composition helper, not repeated scene-walk loops. Policy code decides whether a feature service family should be active; installer code registers authored scene services when present. Neither path should create hidden scene objects to repair setup.

The current Unity-native ownership rule is:

- Siblings describe what a pawn **is**.
- Features describe what a pawn **can do**.
- Participants describe who is **driving**.
- Pawns expose camera sockets through `PawnCameraTarget`; `CameraRigProfile.focusMode` chooses pawn, group, playfield, explicit scene target, or manual Cinemachine focus, while saved reflected Cinemachine recipe entries carry supported lens/body/aim values.
- Scenes own scene-scale direction and services.
- Authoring projects graph truth instead of creating entries or duplicating setup systems.

The source taxonomy now enforces that ownership in assemblies as well as folders. Reusable gameplay code lives under `Modules/*`, route/session composition lives under `Glue/*`, visual and camera routing lives under `Presentation/*`, authored assets and profile helpers live under `Data/*`, and tiny shared contracts/type vocabulary live under `Core/*`. Core runtime contracts are physically grouped by seam family so compile-time language remains easy to browse. Broad gameplay modules should group real subsystems in child folders; Combat, for example, separates health, hit detection, projectiles, status, reactions, flow, pawn combat, enemies, state, and UI instead of keeping all behavior at the module root. The root `NeonBlack.Gameplay` assembly is a thin compatibility facade over `NeonBlack.Gameplay.Glue`; composition should not grow in the root. Combat authored data such as weapons, sequences, projectiles, fire modes, and status effects lives under `Data.Definitions.Combat`; combat behavior lives under `Modules.Combat`; combat service registration lives under `Glue/ServiceRegistration/FeatureInstallers`. Character owns pawn identity, movement, and pawn-facing behavior contracts; Combat consumes Core/Data seams instead of importing Character for motor state, and Character reads combat timing through the Core `IActorCombatMovementInfluence` seam instead of importing Combat. Character should not import Combat. Participant-facing pawn handoff contracts now live under `Data.Participants`: `IPawnParticipantInitializer`, `IPawnParticipantStateReader`, `IPawnRuntimeServicesReceiver`, `PawnRuntimeServicesContext`, `IPawnInputModule`, and `IPawnCombatModule` express participant/profile setup flow, not Character behavior. Interaction dispatch contracts that need participant context live under `Data.Interactions`: `ActorInteractionContext` and `IActorInteractionHandler` let Traversal, RPG, and Interaction-owned components participate in interaction without importing the concrete Interaction module. Feedback presentation lives under `Modules.Feedback`, while `Core.Contracts.IDamageNumberSink` and `Core.Contracts.IActorFeedbackPublisher` are narrow optional sinks/publishers that other modules can use without importing Feedback. `IActorAnimationController`, `IBillboardFacingController`, `IActorCombatMovementState`, `IActorCombatMovementInfluence`, `IActorCombatRequestReceiver`, `ActorCombatCommand`, `IActorCombatResultReceiver`, `ActorCombatResult`, `IActorGuardController`, `IActorGuardInputReceiver2D`, `IActorHazardImpactTarget`, `IActorInteractionInputReceiver2D`, `IActorInteractionRequestReceiver`, `IActorMotionStateReader`, `IActorMovementInputReceiver2D`, and `IEncounterSpawnSource` are Core runtime seams for animation signals, billboard facing control, combat-facing movement state, combat movement influence, combat requests, combat results, guard posture/input, hazard impact immunity, interaction input/requests, motion-state reads, movement input, and encounter spawn progress without concrete opposite-lane imports. `Data.Presentation.IVisualFlashPlayer`, `Data.Presentation.ICameraRigProfileSwitcher`, and `Data.Presentation.IPawnAnimationProfileReceiver` are profile-backed presentation seams for flash entries, camera profile switching, and pawn animation/profile application. Module assemblies should not import `NeonBlack.Gameplay.Glue.*`, ordinary module runtime assemblies should not reference VContainer, and module runtime assemblies should not reference `NeonBlack.Gameplay.Presentation` for concrete animation, visual, camera, or HUD implementations; Presentation implements those Unity components behind Core/Data seams. Input should not import Character, Combat, or Interaction to drive pawn action; it should consume Data participant handoff contracts and Core command/receiver seams. Character owns shared pawn contracts such as traversal interfaces, Traversal owns concrete traversal behavior, and Presentation owns camera targets and camera rigs so camera code does not pull the character module back into presentation.
3D traversal is now split by seam ownership instead of module convenience. `FrameInput` is neutral command data under `Core.Types.Input`. `IPawnTraversalModule`, `IPawnTraversalMovementController`, and `IActorTraversalFeature` live in `Data.Participants` because they express pawn/profile handoff between the concrete movement sibling and traversal module. Traversal runtime no longer imports Character; Character provides the concrete movement controller implementation and Motor3D consumes traversal through Data participant contracts.

The next runtime architecture layer is explicit communication and lifecycle flow. Runtime should move toward typed commands, events, state readers, handlers/sinks, and focused state machines instead of growing concrete module-to-module references or a broad manager. VContainer remains the Glue dependency wiring layer only; it should not become the runtime meaning model. Session and participant lifecycle state machines now live in Glue, pawn locomotion state lives in the Character module, and combat action state lives in the Combat module. `TimeScaleService` owns global time scale and hit pause through `ITimeScaleService`/`IHitPauseSink`; gameplay state that advances over time uses `GameplayTickBehaviour` and `GameplayTickContext` in the owning domain. Presentation, HUD effects, camera smoothing, and local input polling may keep Unity `Update`/`LateUpdate` when they only display or collect state. Authoring/proof state is still the remaining lifecycle owner to formalize. This mirrors the authoring rule in runtime form: compile or expose stable meaning once, then let owners consume narrow projections of that meaning.

`ParticipantDefinition.inputProfile` is the authored input owner. A pawn receives input through its pawn input/movement modules, and `InputProfile` owns the authored Input Action Asset, action-map naming, gameplay action rows, validation, and participant input meaning. For local multiplayer, Unity `PlayerInput` owns the runtime action instance paired to each controller, and `InputProfile.actions` is only the template/naming source. Camera follow is participant-owned and scene-routed: participant pawn assignment exposes the body, pawn prefabs may expose `PawnCameraTarget`, and the scene-owned Cinemachine rig routes the selected focus into Cinemachine. The scene Cinemachine rig is the drafting table; `CameraRigProfile` is the saved recipe/provenance asset; Presentation applies valid recipe entries back to existing Cinemachine components without adding setup components at runtime.

`ParticipantSpawnService` is the single owner for participant pawn placement. `GameplaySessionBootstrap` owns session startup and visible service handoff; it does not store spawn points. Pawn-backed routes assign `ParticipantSpawnService.spawnPoints`; no-pawn routes can leave them empty and disable `Spawn On Register`.

Pawn-backed auto-spawn does not use hidden transform-offset fallback placement. If `Spawn On Register` is enabled, `ParticipantSpawnService` requires an authored spawn point and logs a setup error instead of inventing one. Generic scene/content spawners are optional gameplay utilities, not participant setup surfaces, and their contracts should not appear as route essentials. `PlayerSpawner` is a respawn/lives/countdown coordinator only; it delegates pawn instantiation and placement back to `ParticipantSpawnService` instead of owning separate spawn points.

Gameplay payloads should live with their authored owner instead of in component-local fallback fields. Damage zones require a `HazardImpactProfile`; damage, tick interval, knockback, targeting, and status payloads are profile data. Pawn combat requires authored combat sequences and action definitions for primary and secondary attacks, with aerial sequences required when aerial attacks are enabled. Placeholder service implementations should not stand in for real feature ownership: leaderboard UI can observe an `ILeaderboardService` when a route supplies one, but the package does not register a fake leaderboard manager just to make the UI look configured.

Participant topology is graph evidence, not networking vocabulary. `SessionDefinition.networkMode` describes transport/authority. The graph separately infers whether the active route is `SoloLocal`, `LocalJoin`, `Networked`, or `HybridLocalNetworked` from participant count, pawn gameplay, `PlayerInputManager`, `ParticipantInputRouter.autoRegisterDefaultParticipantsWithoutPlayerInput`, `ParticipantDefinition.autoJoin`, and `ParticipantSpawnService.spawnOnRegister`. Local join routes should wait for Unity `PlayerInputManager` joins; auto-registering every default participant before controllers join is a setup contradiction that Map and Guide should expose.

## Current Authoring State

NeonBlack Gameplay exposes setup evidence through the runtime-safe `Pys.Authoring.Contracts` assembly. The standalone `com.pys.authoring` package owns all authoring UI, graph, projection, export, vocabulary, and hygiene behavior.

```text
Gameplay scripts/assets
  -> PYS contract attributes and local validation providers
    -> observed by com.pys.authoring outside the gameplay package
```

NeonBlack Gameplay owns gameplay meaning and local evidence only:

- runtime-safe `Pys.Authoring.Contracts.AuthoringContractAttribute` metadata on the scripts that own capability meaning
- PYS validation providers where a script or asset owns semantic readiness
- typed setup-flow metadata such as prerequisite stable IDs, route stage/order, setup domain, proof target, and native action kind on the contracts that form the route spine
- Unity-native fields, components, interfaces, definitions, profiles, prefabs, and scene objects
- tactical custom inspectors that edit local fields

PYS owns the Authoring Window, graph compilation, projection packets, Hygiene/Facts lenses, tab rendering, JSON exports, and package vocabulary. Do not rebuild those owners inside the gameplay package, and do not add target-specific adapters around the PYS package. If a projection cannot express a gameplay setup concept, the fix belongs in the PYS package or in clearer gameplay contract/validation evidence.

Inspectors are local integrity surfaces, not setup guides. They may show field-local contract issues, local validation warnings, or small asset-local utilities such as syncing an `InputProfile` from its assigned Unity Input Action Asset. They should not carry route setup cards, genre/preset buttons, alternate proof guidance, projection rows, handoff adapters, or export logic.

PYS exports are external read-only diagnostics from the exact projection packet the PYS UI renders. Current package docs for tab contracts, hygiene lenses, target-project integration, and validation live under `Packages/com.pys.authoring/Docs`.

## Platform Health

The codebase is a usable shared gameplay foundation. The authoring graph carries real setup guidance, and the runtime setup path is understandable from contracts, dependency reflection, and local validators.

Use the latest PYS exports as read-only diagnostics for source/contract ownership, dependency pressure, route setup evidence, and projection health. Export counts are evidence for the current audit moment, not durable architecture truth. Expected composition, editor audit, scanner, vocabulary, and module-owned capability pressure should stay visible without being treated as cleanup work unless a current Hygiene export promotes it into Cleanup Focus.

The main engineering risks are:

- large coordinator files that may need owner-based partials or extracted policies when they stop being readable
- namespace fan-out hiding broad ownership inside otherwise legal assemblies; use Hygiene `NamespaceDependencyFanout` rows to choose decoupling slices before adding more managers
- runtime communication still existing as fragments of interfaces, sinks, UnityEvents, command objects, and services instead of one clear command/event/state-reader/handler vocabulary
- lifecycle state being spread across booleans, service fields, validators, and route guidance; watch for `LifecycleBooleanCluster`, `StateMachineMissing`, and proof/session/participant/pawn/combat transitions that are not explicit
- concrete module-to-module imports remaining legal but hiding behavior coupling; future Hygiene should distinguish accepted same-subsystem edges from `DirectModuleCommunication` pressure
- presentation/animation edges accumulating too much mixed responsibility; camera is being simplified toward target routing plus Cinemachine composition
- route vocabulary that can drift if PYS contracts, reflection, validation, and projection vocabulary do not stay aligned
- Hygiene reporting paper health while runtime feel still needs manual Unity proof passes
- docs re-growing into stale parallel truth
- runtime-created GameObjects being misclassified: spawned gameplay objects, camera focus helpers, popups, fade overlays, and pooled effects are transient runtime output; creating scene services, camera rigs, managers, profiles, or setup objects to repair missing authoring is hidden setup and should stay out of runtime code
- descriptors or exports reintroducing behavior-affecting display-text inference instead of using typed graph metadata, contract role tags, dependency evidence, and validator records
- large public media returning to the always-imported package path instead of explicit samples, Addressables, or route-owned content packages

Optional broad domains are feature-owned rather than mandatory engine spine. RPG value/domain models and definition-facing contracts compile through `Data/Rpg`, while RPG runtime services compile through the RPG runtime module, RPG service registration compiles through Glue, RPG UI/panel presenters compile through the RPG UI module, and RPG-specific editor tooling lives with the RPG feature instead of the universal Authoring Window. Tabletop board and turn value rules compile through `Data/Tabletop/Rules`, while tabletop runtime action resolvers, the current in-memory action queue implementation, selection bridges, and service seams compile through the Tabletop runtime module using Core action contracts, and tabletop scene-facing views compile through the Tabletop UI module. The former one-file Actions module has been collapsed into `Core/Types/Actions`; feature modules provide concrete queue/resolver behavior instead of importing an Actions assembly. Core keeps only small cross-feature type language and neutral utility implementations, with no top-level source files. Current static boundary checks expect zero `Data` imports from RPG/Tabletop runtime modules, zero module-to-Glue imports, zero module VContainer references, zero module scripts falling back into the aggregate root assembly, and an acyclic `.asmdef` graph; runtime/UI asmdef splits are valid when they prevent `Data` and view dependencies from cycling through runtime. If those checks fail, treat it as architecture drift, not a harmless compile detail. Hygiene also audits namespace fan-out now: scripts outside explicit Glue/composition should normally stay at three or fewer `NeonBlack.Gameplay.*` imports, and files above that budget are ownership pressure even when the assembly graph still compiles.

Direct module references are not automatically wrong, but they now require a clear ownership reason. Same-subsystem composition edges and stable module-owned contracts can remain. Cross-subsystem coordination such as pickup-to-score, hazard-to-combat, enemy-to-combat, UI-to-session, and scene-flow-to-gameplay outcomes should move toward typed commands, events, state readers, handlers, or narrow sinks. Do not hide coupling in a generic manager to reduce import counts; the cleanup target is clearer runtime meaning, not prettier metrics.

Current cut lines: collectibles are an Interaction customization lane instead of a separate Pickups module. Collectibles award score through score sink contracts rather than concrete scoring services, and hazard actor targeting/damage uses `IActorHealthState` rather than concrete `HealthComponent`. Hazards remove destroyed collectibles through the neutral `IRemovableFromPlay` contract instead of importing Interaction, read dash-style impact immunity through `IActorHazardImpactTarget` instead of `Motor2D`, apply knockback through `IActorKnockbackController`, apply status effects through the data-owned `IActorStatusEffectSink`, and play authored flash entries through `IVisualFlashPlayer` instead of importing `SpriteFlasher`. Feedback no longer imports Combat for status-effect data or damage-number display; status-effect definitions are authored data, damage-number display flows through the Core sink contract, and combat/enemy/interaction modules publish optional feedback through `IActorFeedbackPublisher` instead of importing Feedback. Scoring reads motion through `IActorMotionStateReader` and optional death state through `IActorHealthState` instead of importing Character. Input drives 2D movement through `IActorMovementInputReceiver2D`, interaction through `IActorInteractionInputReceiver2D`, guard through `IActorGuardInputReceiver2D`, and combat through `ActorCombatCommand`/`IActorCombatRequestReceiver`; the Input runtime assembly no longer references Character, Combat, or Interaction. Character forwards interaction input through `IActorInteractionRequestReceiver` instead of importing the Interaction module; Interaction owns `ActorInteractionComponent`, which implements that Core request seam directly, while shared interaction handler dispatch uses `Data.Interactions`. Encounters activate and observe spawners through `IEncounterSpawnSource` instead of importing the Spawning module or Character participant helpers, and switch camera profiles through `ICameraRigProfileSwitcher` instead of importing the concrete Cinemachine rig. Pawn combat scripts moved from Character into Combat, so Character no longer imports Combat for combat behavior. Combat reads pawn facing, airborne, grounded, and action-lock state through `IActorCombatMovementState`; Character reads combat movement timing and multipliers through `IActorCombatMovementInfluence`; Character drives animation through `IActorAnimationController` instead of importing the concrete `ActorAnimationDriver`; Combat and Character runtime assemblies no longer need to reference each other or Presentation for those seams. Enemy runtime no longer depends on Character; participant target lookup flows through `Data.Participants`, and outgoing combat modifiers use the Core `IActorCombatModifierReceiver` seam. Enemy movement-facing also uses the Core `IActorFacingMirrorTarget` seam instead of importing Combat hitbox slots directly, and billboard facing uses `IBillboardFacingController` instead of importing Presentation visuals. Player/participant input and enemy AI now issue combat intent through `ActorCombatCommand` and `IActorCombatRequestReceiver`; pawn combat and enemy combat publish attack/combo presentation facts through `ActorCombatResult` and `IActorCombatResultReceiver`; combat timing is owned by combat components through `GameplayTickBehaviour` instead of being manually ticked by Character or Enemy. Enemy hitbox/combat-module dependencies remain accepted same-capability composition until hit resolution itself becomes a fuller combat-result event stream.
Traversal runtime now reads the 3D movement sibling through `IPawnTraversalMovementController`, applies traversal profiles through `IPawnTraversalModule`, and exposes optional traversal through `IActorTraversalFeature`. The remaining Character names in Traversal are setup strings for authoring/inspector guidance, not assembly dependencies.
Enemy runtime already sends attack intent through `ActorCombatCommand` and `IActorCombatRequestReceiver`. Enemy editor ownership now matches that runtime seam: `EnemyAIEditor` owns detection, movement, patrol, targeting, and enemy feature profile fields, while `EnemyCombatModuleEditor` lives in the Combat editor assembly and owns enemy attack profiles, hitboxes, sequencing, cooldowns, and attack range tuning. The remaining Combat names in Enemies are setup strings for HealthComponent guidance, not assembly dependencies.

Hygiene now has source-derived runtime communication pressure categories for direct module communication, lifecycle boolean clusters, missing state-machine owners, event-channel overuse, and manager behavior leaks. These are code ownership audit rows only; they should not become Map or Guide setup instructions.

## Maintenance Focus

1. Keep one owner for each gameplay responsibility.
2. Keep runtime simple and Unity-native before adding abstraction.
3. Keep contracts semantic; reflection owns structure that code can prove.
4. Keep Authoring as graph projection, not a second setup system.
5. Keep active docs small, current, and direct.
6. Keep optional feature domains broad but locally owned; do not let a feature's service list or editor tool turn into universal core.
7. Keep generated diagnostics such as PYS Authoring exports out of source control and outside imported asset/package folders; use them as evidence, not durable docs.
8. Keep runtime communication explicit: commands request work, events report facts, state readers expose current state, handlers/sinks react, and state machines own lifecycle transitions.
9. Keep gameplay time explicit: rule-changing timers tick through the owning domain, while display-only animation and input polling stay local to their Unity component.

## Verification Posture

Use Unity Test Runner or `.\Tools\Validation\Run-PreSceneValidation.ps1` as the durable gate when runtime/editor code changes. For docs-only consolidation, use link/reference checks and `git diff --check`.

Manual Authoring Window walkthroughs are still required for user-flow confidence because static tests can prove graph shape but not whether the setup feels clear.

The default test gate should stay focused on seam protection rather than fake gameplay confidence:

- **Manual play proofs** answer whether the game actually feels and works in Unity.
- **Automated tests** protect data transfer, ownership, routing, contracts, graph projections, exports, and refactor seams.
- **Authoring exports** show what the system currently understands.

Old broad feature-domain matrices, documentation contract audits, classifier detail sweeps, and source-text tests have been removed from the active package. Add new automated tests only when they protect a current seam, data transfer, route projection, or runtime ownership rule. Do not add tests that only lock source prose, stale docs, or simulated gameplay claims that still require a Unity proof.
